## Стратегический роадмап трансформации «Будущее 2.0»

Трансформация разделена на 12 последовательных шагов, сгруппированных по годам, для обеспечения плавного перехода к модели **Data Mesh** и событийной архитектуре (EDA).

---

### Год 1: Фундамент и пилотные интеграции
*Фокус на создании защищенного контура и запуске событийной модели в медицине.*

1.  **Этап 1: Инфраструктурный старт (0–3 мес).** Развертывание **Virtual Private Cloud (VPC)** и выделенных хостов для соблюдения требований 152-ФЗ. Запуск базового кластера **Kafka** (Event Streaming Platform) и Schema Registry.
2.  **Этап 2: Security & IAM (3–6 мес).** Внедрение **Keycloak** для централизованной аутентификации и **HashiCorp Vault** для управления секретами и токенизации персональных данных.
3.  **Этап 3: Пилот в Медицине (6–9 мес).** Реализация событий `PatientRegistered` и `AppointmentCompleted`. Создание первого **Data Product** (витрина пациентов) на базе S3 и Apache Iceberg.
4.  **Этап 4: Запуск B2B Gateway (9–12 мес).** Развертывание шлюза для внешних партнеров (фарма, IoT-оборудование) с использованием **Anti-Corruption Layer (ACL)** для изоляции внутреннего контура.

---

### Год 2: Экспансия доменов и аналитическая платформа
*Фокус на подключении Финтеха, ИИ и запуске федеративного поиска данных.*

5.  **Этап 5: Онбординг Финтех-домена (12–15 мес).** Интеграция сервисов биллинга и кредитования. Публикация событий `InvoiceCreated` и `InvoicePaid` в общую шину.
6.  **Этап 6: Интеграция ИИ-сервисов (15–18 мес).** Перенос ML-моделей в облако. Реализация асинхронного цикла анализа через события `AIAnalysisRequested` и `AIAnalysisCompleted`.
7.  **Этап 7: Развертывание Trino (18–21 мес).** Запуск федеративного движка запросов для прямого чтения данных из S3-хранилищ доменов без физического копирования.
8.  **Этап 8: Data Governance & Catalog (21–24 мес).** Внедрение **DataHub** для каталогизации всех доступных витрин данных. Назначение ролей **Data Stewards** в каждом бизнес-домене.

---

### Год 3: Миграция и достижение целевого состояния
*Фокус на выводе легаси-систем и оптимизации стоимости владения (TCO).*

9.  **Этап 9: Вытеснение легаси в Медицине (24–27 мес).** Перевод интерфейсов с PowerBuilder на новые веб-сервисы. Постепенное отключение маршрутов в старой шине Camel для медицинского домена.
10. **Этап 10: Миграция финансовых данных (27–30 мес).** Окончательный перенос истории транзакций и счетов из старого DWH (MS SQL 2008) в целевое хранилище на базе PostgreSQL и S3.
11. **Этап 11: Decommissioning (30–33 мес).** Полное отключение серверов MS SQL Server 2008 и демонтаж инфраструктуры Apache Camel.
12. **Этап 12: Оптимизация и Self-Service (33–36 мес).** Финальный тюнинг **near-real-time** потоков. Обучение всех бизнес-пользователей работе с аналитическим порталом в режиме самообслуживания.

---

### Роли и ответственность на этапах
| Роль | Зона ответственности | Участие в этапах |
| :--- | :--- | :--- |
| **Data Product Owner (DPO)** | Определение ценности данных домена (Медицина, Финтех, ИИ) и контроль качества «Дата-продуктов». | Все этапы |
| **Platform Engineer** | Поддержка **Event Streaming Platform (Kafka)**, Kubernetes и облачного контура **VPC**. | 1–12 |
| **Security Engineer** | Настройка **IAM (Keycloak)**, ротация ключей в **Vault** и обеспечение комплаенса (152-ФЗ, PCI DSS). | 1–4, 9–11 |
| **Data Engineer** | Разработка CDC-потоков (Debezium), хранилищ (S3 + Iceberg) и пайплайнов для доменных Data Lakes. | 1–10 |
| **API Architect** | Проектирование **B2B API Gateway** и реализация **Anti-Corruption Layer (ACL)** для изоляции легаси. | 2–9 |
| **Data Steward** | Ведение каталога данных (**DataHub**), управление метаданными и контрактами событий. | 4–12 |
| **BI-аналитик** | Создание федеративных отчетов через **Trino** и обучение бизнес-пользователей самообслуживанию. | 6–12 |
| **Legacy Developer** | Поддержка работоспособности систем на PowerBuilder/Camel и помощь в их безопасном выводе из эксплуатации. | 1–11 |
